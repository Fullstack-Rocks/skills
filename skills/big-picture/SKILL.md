# Big picture

The graph is built by programs, never by reading: lizard finds functions, SCIP indexers give exact calls, ast-grep rules find the project's own node types and connections, and the `call-depth` and `code-standards` skills supply health. Your part is to **teach** it: when a convention of this codebase isn't in the graph yet, you write it down once as an ast-grep rule, and every later build finds it for free.

Agents read the result through the `big-picture-query` skill (`bp node`, `bp neighbors`, `bp find`). Use it to check your work.

Everything in `.big-picture/` except `out/` is the team's memory of the codebase and is meant to be committed; say so when you create or change it. `out/` is regenerated by every build and ignored through `.big-picture/.gitignore`.

## Tools

Scripts are in this skill's `scripts/` folder, Python 3.11+, standard library only. They need:

- **ast-grep** and **lizard**, from the `call-depth` skill: `python3 <call-depth>/scripts/install_tools.py ast-grep lizard`
- the **SCIP indexers** for exact calls: `python3 scripts/install_tools.py` (needs Node.js; pinned, installed at user level). Without one, that language's calls are built by name and marked approx.
- the `call-depth` skill installed next to this one for health; `code-standards` too when the project has a `.code-standards/` folder.

Install what's missing yourself and tell the developer in one line what was installed.

## Build

1. When the root holds more than the project (worktree copies, prototypes), list the project's folders in `.big-picture/config.yml` as `include: [Backend, web]`; only they are built. Files `.gitignore` ignores, `node_modules` and virtualenvs, and minified JavaScript are always left out. Run `python3 scripts/build.py <project root>`. It prints one line: node, edge and finding counts, rule matches, the call source per language (`scip` or `approx`) and the time.
2. Read every warning above that line (a failed indexer, a skipped health source) and fix or report it.
3. Check coverage with `big-picture-query`: `bp find --type endpoint`, then `bp node` on one endpoint and one table. When a convention is missing (endpoints with no handler, a data layer with no table nodes), **teach** it.
4. **Survey** the project for every part of the overall system the graph doesn't show yet, and teach each one before you report the build:
   - **Database.** Tables with no columns in `bp db`, or none at all, mean the schema lives in ORM models or migrations. When no `.sql` file declares it, add to `.big-picture/config.yml` a `schema_commands` entry, run from the project root, that prints the DDL. For SQLAlchemy, use `<the project's python> -I {scripts}/sqlalchemy_ddl.py <models package> <module:Base>`; for another ORM, its own DDL or offline-migration command. Then teach the edge from each model to its table.
   - **Services and infrastructure.** In every Compose file, Kubernetes manifest, Procfile and infrastructure-as-code config (SST, Terraform, CDK, Pulumi), each service, gateway, proxy, cache, queue, emulator and cloud resource gets a lens (**Add a lens**), along with the links between them (`depends_on`, routes).
   - **External clients.** For each client library in the manifests that the code imports (Redis or Valkey, Kafka, RabbitMQ, Celery, boto3 or the AWS SDK, payment and mail SDKs), the service it reaches gets a node, with an edge from every module that uses it.

Done when the build prints no warning you haven't reported, every route style and data-access pattern the developer would name has nodes, and every service in each Compose or infrastructure file, every external client the code imports, and every table the models declare is a node connected to what uses it. Anything you didn't teach is listed to the developer, with the reason.

## Teach a convention

1. Find the convention in the code: a decorator, base class, call shape or naming pattern that repeats and means something (a route, a job, a table access).
2. Read [`references/node-types.md`](references/node-types.md) and write the rule: `.big-picture/types/<id>.yml` for a new kind of node, `.big-picture/edges/<id>.yml` for a connection from the code around a match to a node, `.big-picture/properties/<id>.yml` for values that belong to a node (a model's fields, which become its table's columns). Create `.big-picture/sgconfig.yml` from that reference if the project has none.
3. Write `.big-picture/rule-tests/<id>-test.yml`: at least two `invalid` cases the rule must match and two `valid` near-misses it must not.
4. Run `ast-grep test -c .big-picture/sgconfig.yml --skip-snapshot-tests` until it passes.
5. Count the convention by hand (`grep -c` on its plainest spelling) and compare with the rule's hits: `ast-grep scan -c .big-picture/sgconfig.yml --json=compact | python3 -c "import json,sys,collections; print(collections.Counter(m['ruleId'] for m in json.load(sys.stdin)))"`. A gap means the rule misses spellings or matches too much; refine it and rerun.
6. Rebuild and check the new nodes with `bp node`.

Done when the fixtures pass, the hit count matches the hand count (or the difference is explained), and `bp node` shows the new nodes connected.

## Explain nodes

Write a note for each node a reader needs explained: `.big-picture/docs/<slug>.md`, where the slug is the node id with every run of characters other than letters, digits, `.`, `_` and `-` turned into `_` (`fn:app/db.py#get_db` -> `fn_app_db.py_get_db.md`).

```markdown
---
node: fn:app/db.py#get_db
source_hash: <the hash `bp node` prints for it>
---
What it is for, how to call it (a short example), what it touches, and what to watch out for.
```

The viewer shows a note as soon as it is written, without a rebuild; the next build marks it stale when the code under it changes, so rewrite stale notes. For many notes at once, when the developer wants it, fan the writing out per capsule with the `delegate` skill: one delegate per capsule, each given `bp capsules` and `bp node` output.

Done when every node you were asked to explain has a note whose hash matches.

## Name capsules

The build groups modules that work together into capsules (`bp capsules`), leaving out shared modules every capsule uses (listed under `coverage` in the build line). Name them, and pin a module that landed in the wrong one, in `.big-picture/capsules.yml`:

```yaml
names: { app/services/order_service.py: Orders }               # key: the capsule id after capsule:
pins:  { app/models/order.py: app/services/order_service.py }   # module: a module in the capsule it belongs to
```

## Connect systems

Systems are the deployable units (a backend, a frontend, a worker): folders with their own manifest, or each top-level code folder when one manifest covers the project. Set them yourself in `.big-picture/systems.yml` (`systems: {api: services/api, web: apps/web}`) when that guess is wrong. Nothing about how systems talk is built in; teach each channel you find as rules:

1. **Find both sides.** For each way the systems talk (HTTP through a generated or hand-written client, a queue or event bus, a socket, RPC), find the code that serves or publishes and the code that calls or consumes.
2. **Shared names become a shared node.** When both sides spell the same literal (a topic `order.created`, a socket message `price.update`), give both sides an edge rule to the same id: `to: "topic:{TOPIC}"`. That node is the contract.
3. **Names that differ become keys.** When the two sides spell it differently (a route `/orders/{id}` against a client's `` `/orders/${id}` ``, or a generated client's `getOrderTotal()` against an `operationId`), give the serving side `keys` in its type rule (`keys: ["http:{METHOD|upper} {PATH|route}"]`) and point the calling side's edge rule at `~` plus the same key (`to: "~http:{VERB|upper} {PATH|route}"`). OpenAPI operations carry `http:` keys already.
4. Rebuild, then check `bp systems`: every channel you found should be listed, and the build line's unresolved-contracts count should be 0. Each unresolved one is a finding naming the caller.

Done when `bp systems` lists every channel between the systems, and the Systems tab shows them.

## Add a lens

When you find a subsystem the graph doesn't show yet (a cache, message queues, Docker services, nginx routes, config files whose keys change behaviour, `.env` keys, feature flags), give it a **lens**: its own nodes, connections and tab, written as files only.

1. Teach its parts as rules (**Teach a convention**). Use an ast-grep rule where ast-grep parses the file; for files it can't parse (`.env`, nginx, INI, Dockerfiles), write a **pattern rule**, `.big-picture/patterns/<id>.yml`, a regex with named groups and the same metadata. Capture names and keys, never secret values. The format is in [`references/node-types.md`](references/node-types.md).
2. Write `.big-picture/views/<id>.yml`: `title`, the node `types` it shows, the `edges` kinds it follows, `neighbors: true` to include the code on the other end, and `colors` for each type and kind.
3. Colour from the technology's own brand: look up its logo colours (Redis `#DC382D`, Valkey a gradient `linear-gradient(135deg, #4F46E5, #A855F7)`, nginx `#009639`, Docker `#2496ED`, dotenv `#ECD53F`). A gradient is fine where the brand uses one.
4. Rebuild, then check with `bp view <id>` and the new tab.

Done when the lens's tab shows every part you found, each connected to the code that uses it, and its fixtures pass.

## View

- **Live:** `python3 scripts/serve.py <project root>` serves the viewer at http://localhost:7478. The page rechecks the graph every 2 seconds, so a rebuild shows up without a reload, and the node pane reads source lines straight from the project. Run it in the background and give the developer the URL. To point at one node, append `#/n/<url-encoded node id>`.
- **What the viewer shows:** the Map tab (the project birds-eye, folders and modules as frames; dive into any node), the Capsules tab, the Database tab (tables, views and JSON lookups with their columns, keys and relations), the Endpoints tab (OpenAPI operations beside the code that implements them, with Try it), the Health tab (everything with findings), and one tab per lens. Clicking a node opens its pane: a description, its connections with the code line of each, its health findings with how to fix them (and a brief to copy for an agent), its table structure, and its source. Clicking a line focuses that connection. Dragging a card pushes its neighbours and grows its frame; a selected frame's options bar re-arranges its contents.
- **Share:** `python3 scripts/export.py <project root>` writes `.big-picture/out/big-picture.html`: one file with the graph inside, which opens from disk. It is a snapshot: it shows no source and doesn't follow rebuilds.

The viewer ships prebuilt as `viewer/dist/index.html`. Node is needed only to change it: `npm ci && npm run build` in `viewer/`, then commit `dist/index.html`.

## Check the build itself

`python3 tests/check_fixture.py` builds `tests/fixture` (SQL DDL with every table kind, keys, constraints and indexes; JSON lookups in code and in a view; a repeated query) and checks what the stages must find. Run it after changing a stage.

## Graph format

[`references/graph-schema.md`](references/graph-schema.md) defines `graph.json`. A change to a field's meaning bumps `SCHEMA_VERSION` in `scripts/graph.py`, `viewer/src/data/load.ts` and `big-picture-query`'s `scripts/graph/load.py` together.
